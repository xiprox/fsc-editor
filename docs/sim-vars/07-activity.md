Activity does not start and stop. **It segments.**

Once connected, the module diffs continuously and streams changes into a
rolling buffer. What turns that stream into something readable is the *anchor*.

## Anchors unify everything

An input event, an H: event and a hotkey mark are the same object: a timestamped
anchor. One is generated by the sim, one by the DOM layer, one by the user when
the sim did not generate either. Everything downstream treats them identically.

So the output is not a window you request. It is **a list of findings that grows
as you interact** — the closest analogue is a browser's network tab. Touch a
switch in the cockpit and a row appears: the input event's name, the gesture,
and how many variables moved. Click to expand.

The hotkey then has exactly one job, and it is the hard case named in
[01-goals](01-goals.md): **background state, where nothing was touched.** A mark
creates a segment where the sim would not have made one. See
[08-marks](08-marks.md).

## What a finding contains

**Two tiers, not one window.** Flip a battery master and one variable changes
directly while eighty follow as the bus energizes. Those are not the same thing:

- **direct** — within roughly 150–250 ms of the anchor. This is what gets bound.
- **downstream** — the next ~3 s. Context, collapsed by default.

Each row: variable, before → after, Δt from the anchor.

**Repeats collapse, and correlation comes free.** Touch the same control five
times and it is one finding seen 5×, not five findings. The expansion shows
consistency — *these two changed all five times; these three changed once*.
That is repeat-and-correlate arriving without anybody being told to do it,
because flipping a switch a few times while working out what it does is what
people already do.

## Ambient noise classifies itself

Anything that changes without ever landing near an anchor is ambient by
definition, and demotes itself over time. Running continuously means no
explicit idle pre-roll is needed — the classifier falls out of the design.

Ambient changes stay in the buffer and out of the feed. A retroactive mark can
still reach them, which is the whole point of the background-state case.

## Separators

The feed shows breaks in continuity as separator rows: **aircraft changed**,
**sim paused**, **connection lost**. A finding from before an aircraft change is
about a different aircraft and must not read as continuous with what follows.

## Empty states

Three, and each says something different:

- **Not connected** — this is the best place to explain what connecting buys,
  so it carries the pitch and the same CTA as the footer chip. See
  [04-connection](04-connection.md).
- **Connected, aircraft has few input events** — "this aircraft defines 5 input
  events; use a mark to capture a window." Not a blank list. The count comes
  from Analysis and is knowable in advance ([02-namespaces](02-namespaces.md)).
- **Connected, nothing has happened yet** — go touch something.

## Panel

Bottom panel, two columns:

- **left**: the findings feed, narrow, resizable
- **right**: the selected finding's table, wide, **always occupying its space**
  with a "select a finding" placeholder so nothing jumps when selection changes

Header carries live/paused, the bound hotkey, the current aircraft, clear, and
close. Full layout in [15-ui-surfaces](15-ui-surfaces.md).

## Not in v1

**No timeline.** The feed model absorbed most of its job: order is list order,
and interaction-anchored findings have a precise anchor and fixed tiers, so
there is nothing to drag.

Where it would eventually earn its place is inside an expanded *mark-anchored*
finding — window adjustment, and more importantly an interaction lane showing
what you touched seconds before the thing you marked. That is a causal hint no
table gives, because the answer is an action outside the list.

A Δt column plus fixed tiers covers v1. The decision that keeps the timeline
available later is the storage one in [08-marks](08-marks.md): persist wide,
display narrow.
